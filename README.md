Saat pengguna membuka halaman portofolio baru, alurnya adalah : request dari first browser diterima 'urls.py' pada level proyek seperti portofolio/urls.py, yang tugasnya adalah match path URL dengan pola yang ada. Karena path 'education/' diarahkan dengan 'include()' ke app 'main', permintaan kemudian dikirim ke 'urls.py' pada level aplikasi main/urls.py, yang mencari pola URL spesifik dan memetakannya ke fungsi view yang sesuai yaitu show_education. View ini kemudian mengambil seluruh data dari model 'Education' dengan 'Education.objects.all()', memasukkannya ke dalam sebuah context dan meneruskan context nya ke template 'education_list.html' menggunakan fungsi 'render()'. Template kemudian menggunakan Django Template Language untuk melakukan perulangan ('{% for %}') terhadap data pada context, menampilkan setiap objek Education dalam bentuk HTML, sebelum akhirnya HTML tersebut dikirim kembali sebagai response dan ditampilkan oleh browser.

Data untuk bagian portofolio baru sebaiknya disimpan pada model dan tidak ditulis langsung di dalam template karena beberapa alasan utama. Pertama, memisahkan data dari tampilan (separation of concerns) membuat data menjadi terstruktur dan dapat dikelola melalui database, sehingga perubahan data (menambah, mengedit, atau menghapus) tidak memerlukan perubahan kode HTML maupun proses deployment ulang. Kedua, data yang tersimpan di model dapat divalidasi, difilter, atau diurutkan dengan mudah menggunakan Django ORM sebelum ditampilkan. Ketiga, hal ini juga membuat pengujian (testing) menjadi lebih mudah, karena skenario data kosong maupun data terisi dapat disimulasikan langsung melalui model tanpa perlu mengubah template. Jika data ditulis langsung (hard-coded) di HTML, aplikasi menjadi sulit dikembangkan dan rentan terhadap duplikasi maupun inkonsistensi data di berbagai halaman.
`makemigrations` berfungsi untuk membuat berkas migrasi baru berdasarkan perubahan yang dilakukan pada model (misalnya menambah model baru, menambah/mengubah field), namun perintah ini belum benar-benar mengubah struktur database, hanya menghasilkan "rencana perubahan" dalam bentuk berkas Python di folder `migrations/`. Sementara itu, `migrate` berfungsi untuk benar-benar menerapkan (mengeksekusi) perubahan yang tercatat pada berkas migrasi tersebut ke dalam skema database yang sesungguhnya. Contoh kasus yang mengharuskan menjalankan kedua perintah tersebut adalah ketika membuat model baru `Education` pada tugas ini: setelah menambahkan class `Education` di `models.py`, perintah `python manage.py makemigrations` dijalankan untuk menghasilkan berkas migrasi baru (`0002_education.py`) yang mendeskripsikan tabel baru tersebut, kemudian perintah `python manage.py migrate` dijalankan untuk benar-benar membuat tabel `Education` pada database sesuai skema yang telah didefinisikan.
